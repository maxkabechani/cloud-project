# HPC Cloud

A TypeScript university Beowulf cluster management application using **Bun**. Local development uses **SQLite**; deployment will use **PostgreSQL**. No Docker or database installation is needed to work locally.

## Current scope

The local milestone is complete: registration and login, protected workspace navigation, member directory, role-aware VM management, cluster node health, cloud-account provisioning, an activity trail, and predefined MPI job submission are all available. The web API uses a persisted mock provider locally, while the private cluster-agent package defines the authenticated control-plane boundary for a future OpenNebula deployment. Nothing has been publicly deployed.

## Start locally

Prerequisite: Bun 1.4.2 or a newer compatible version.

From the repository root:

```sh
bun install --frozen-lockfile
bun run setup:local
bun run dev
```

Open [the registration page](http://localhost:3000/register) and create your own account. Passwords must have at least 12 characters. The API listens at [localhost:4000](http://localhost:4000/health).

The setup command creates missing local environment files, generates a random authentication secret, and applies SQLite migrations. It preserves existing files and refuses to switch an existing PostgreSQL configuration silently. Running setup again is safe: existing accounts and secrets are preserved.

The public API uses the mock provider by default, so the web app and API are enough for local development. To exercise the private control-plane boundary as well, set a 32-character `CLUSTER_AGENT_API_KEY` in `apps/cluster-agent/.env` and run `bun run --filter @hpc/cluster-agent dev` in a second terminal.

SQLite data is stored at **`.local/hpc-cloud.sqlite` in the repository root**, independently of which workspace runs the API or migration command. Accounts and sessions survive restarts. The database, its WAL files, and local environment files are ignored by Git. `SQLITE_PATH` may override the path; relative paths are always resolved from the repository root.

Use `localhost` consistently in the browser and environment URLs; mixing it with `127.0.0.1` changes cookie/origin behavior. Shut down a previous server before running another copy on the same ports.

## Admin account

Set `ADMIN_NAME`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD` in `apps/api/.env`, then run:

```sh
bun run db:seed
```

This works with either database. Better Auth creates and hashes the credential; the seed script grants the role server-side. It does nothing if the admin already exists and refuses to promote an existing member with that email. Remove the bootstrap password from the environment afterward. Do not run concurrent seed commands.

## Database selection

Local defaults in `apps/api/.env`:

```dotenv
NODE_ENV=development
DATABASE_PROVIDER=sqlite
SQLITE_PATH=.local/hpc-cloud.sqlite
DATABASE_URL=
BETTER_AUTH_SECRET=<generated by setup:local>
BETTER_AUTH_URL=http://localhost:4000
WEB_URL=http://localhost:3000
```

For the later PostgreSQL deployment:

```dotenv
NODE_ENV=production
DATABASE_PROVIDER=postgres
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DATABASE
BETTER_AUTH_SECRET=<production secret>
BETTER_AUTH_URL=https://api.example.edu
WEB_URL=https://cloud.example.edu
HOST=0.0.0.0
PORT=4000
```

Set `NEXT_PUBLIC_API_URL=https://api.example.edu` on the frontend before its production build. Production configuration requires PostgreSQL and HTTPS.

After setting the deployment environment, run `bun run db:migrate`, then start the API with `bun run --filter @hpc/api start`. The same command selects the correct migrations from `DATABASE_PROVIDER`.

**Changing providers does not copy data.** SQLite and PostgreSQL use separate databases and migration histories. For a clean deployment, migrate an empty PostgreSQL database and create the production admin. If local accounts need to be carried over, plan an explicit export/import before deployment, preserving user IDs and Better Auth credentials and converting timestamps/booleans. A SQLite file or SQL dump cannot simply be applied as a PostgreSQL migration. Data transfer is not implemented in this phase.

The optional `compose.yaml` remains available for PostgreSQL testing with `docker compose up -d postgres`. Its localhost development URL is `postgresql://hpc:local-development-only@localhost:5432/hpc_cloud`; these example credentials are not for deployment.

## Migrations

```sh
bun run db:generate   # Generate both dialects after a schema change
bun run db:migrate    # Apply only the configured dialect
```

Keep both schemas aligned when adding fields. SQLite uses integer millisecond timestamps and integer booleans; PostgreSQL uses timezone-aware timestamps and booleans. Drizzle maps both to the same JavaScript domain values.

The committed PostgreSQL migration history remains in `packages/db/migrations`. SQLite has its own history in `packages/db/migrations-sqlite`. Migrations are repeatable and do not reset the database. SQLite connections enable foreign keys, WAL, and a bounded busy timeout. Better Auth owns password hashing and authentication records in both providers.

## Architecture

```text
Browser
   |
   v
Next.js
   |
   v
Public Fastify API
   |         |
   |         +--> SQLite locally / PostgreSQL on deployment
   |
   v
Cluster Agent             (private, authenticated control plane)
   |
   +--> OpenNebula         (provider adapter boundary)
   |
   +--> MPI               (future, predefined programs only)
   |
   v
Beowulf Cluster
```

Identity and data go through Fastify; the frontend never connects to the database or OpenNebula. Authentication does not depend on a physical cluster being online. Switching database providers requires no frontend change.

## Security and deployment notes

Better Auth handles credentials, session expiration, and cookies. The API validates the frontend Origin for authentication mutations, restricts CORS, redacts sensitive request headers, limits request sizes and rates, and uses Helmet. Registration and profile updates cannot set roles. `/api/me` checks the persisted session and returns only public profile fields with private/no-store caching.

Auth rate limits are currently per-process. Configure shared rate-limit storage and a reviewed proxy/IP setup before horizontal scaling. Email verification and password recovery delivery are not configured yet; add a mail provider and university enrollment policy before a public production launch.

Deploy Next.js and Fastify independently with externally managed PostgreSQL. Use HTTPS subdomains of the same site, such as `cloud.example.edu` and `api.example.edu`, for normal SameSite cookie behavior. Unrelated hosting domains need a deliberate cookie/proxy design and browser testing. Preserve the browser Origin through proxies.

## Provider integration

## MPI Jobs

MPI workloads are submitted only as predefined programs. The browser sends a program identifier and validated process count to the public API. The API authorizes the user and forwards the controlled request to the private cluster agent, which will eventually invoke the approved MPI program with `mpirun` across the Beowulf nodes.

```text
Website → Fastify API → Cluster Agent → mpirun → Beowulf nodes
```

The browser never sends shell commands, executable paths, or raw arguments. Local development uses the deterministic mock MPI provider, so jobs can be demonstrated before the physical cluster is connected.

## Performance Benchmarking

Benchmarks execute the same approved workload at several process counts and record each run. If `T1` is the single-process execution time and `Tp` is the parallel execution time:

```text
Speedup:   S(p) = T1 / Tp
Efficiency: E(p) = S(p) / p
```

The results show the performance benefit of parallel execution and its limitations: communication, coordination, and scheduling overhead can reduce efficiency as the process count increases.

## Smart VM Placement

Automatic VM placement evaluates online nodes using available CPU, available RAM, and running VM count. The provider selects the least-loaded suitable node and returns the final host to the dashboard. Manual placement is limited to registered online nodes.

When OpenNebula is active, its scheduler may remain authoritative. The dashboard will display the placement returned by the provider rather than attempting to override platform scheduling.

The cluster agent accepts future MPI configuration through `MPI_USER`, `MPI_HOSTFILE`, and `MPI_PROGRAM_DIRECTORY`. These values are intentionally environment-driven and are not assumed to exist on the development machine.

## Provider integration

The `CloudProvider` interface and persisted `MockCloudProvider` make local development deterministic. The cluster agent exposes only explicit status, node, user, VM, and MPI routes and has no shell or arbitrary command endpoint. Its `OpenNebulaClient` is an isolated adapter boundary that fails closed until the exact provider version, endpoint, service account, templates, networks, quotas, and connectivity details are supplied.

Before real integration, obtain the OpenNebula version, documented endpoint/protocol, service-account permissions, approved templates/images, networks, quotas, and master-node connectivity details. No speculative OpenNebula endpoints are present. MPI will allow only predefined programs, never arbitrary browser-supplied shell commands.
